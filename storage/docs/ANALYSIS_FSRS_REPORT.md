# FSRS 도입을 위한 코드베이스 분석 및 냉정 피드백

현재 `learning_japanese` 프로젝트의 코드베이스와 DB 구조를 바탕으로, FSRS 알고리즘을 도입하기 위해 필요한 준비 사항과 현재의 문제점을 냉정하게 분석한 보고서입니다.

## 1. 종합 진단: "기초는 있으나 설계의 파편화가 심각함"
현재 시스템은 SM-2 기반의 로직을 사용하고 있지만, 데이터의 저장 방식이 여러 테이블(`user_kana_progress`, `user_vocabulary`, `mastery_records`)에 흩어져 있습니다. 이 상태에서 FSRS를 도입하는 것은 **"모래성 위에 성채를 쌓는 격"**입니다.

---

## 2. 상세 분석 (Gap Analysis)

### A. 데이터 모델 (Database) - **[가장 시급함]**
- **현상**: `user_vocabulary` 테이블은 SM-2 전용 컬럼(`interval`, `ease_factor`)만 보유 중.
- **부족한 점**: FSRS 실행에 필수적인 `Stability`(안정성), `Difficulty`(난이도), `Lapses`(망각 횟수), `State`(학습 상태) 컬럼이 전무함.
- **피드백**: 테이블 구조를 전면 개편하거나, 모든 학습 대상을 수용할 수 있는 `mastery_records`로 통합하는 정지 작업이 선행되지 않으면 FSRS의 정밀한 계산 결과가 증발하게 됩니다.

### B. 비즈니스 로직 (Core Engine)
- **현상**: `src/lib/srs.ts`에 매우 단순한 SM-2 수식만 하드코딩되어 있음.
- **부족한 점**: FSRS는 수식이 복잡(로그 및 지수 함수 기반)하고, 유저의 과거 데이터를 기반으로 가중치(Weights)를 최적화하는 미분 과정이 필요함. 
- **피드백**: 단순한 함수 하나가 아니라, `FSRSEngine` 클래스 형태의 전용 모듈이 필요합니다. 또한 '그저께 틀렸는데 오늘 맞힌 것'과 같은 **시계열 데이터**를 처리할 준비가 되어 있지 않습니다.

### C. 인터렉션 (UI/UX)
- **현상**: 학습 결과 반영 시 '맞음/틀림' 수준의 이분법적 입력 위주.
- **부족한 점**: FSRS의 성능을 100% 끌어내려면 유저로부터 **4단계 반응(Again, Hard, Good, Easy)**을 받아야 합니다.
- **피드백**: 현재의 미니멀한 UI를 유지하면서도 유저에게 4단계 피드백을 어떻게 세련되게 받을 것인지에 대한 UX 설계가 누락되어 있습니다.

---

## 3. 냉정한 피드백 및 로드맵 제안

> [!CAUTION]
> **냉정한 한 줄 평**: 현재의 데이터 파편화 상태에서 알고리즘만 FSRS로 바꾸는 것은 "엔진만 페라리로 바꾼 낡은 트럭"과 같습니다. 먼저 데이터 구조를 하나로 묶는 **'중앙 집중형 학습 데이터 계층'** 구축이 필수입니다.

### 🛠 성공적인 도입을 위한 3단계 전략

1.  **데이터 통합 (Centrally Managed Records)**:
    - 가나(`KANA`)와 단어(`CHUNK`) 기록을 하나의 `mastery_records` 테이블로 강제 통합.
    - FSRS용 파라미터(`Stability`, `Difficulty` 등)를 위한 스키마 확장.

2.  **엔진 이식 (Algorithm Porting)**:
    - `src/lib/fsrs.ts` 생성 및 공식 FSRS v4 가중치 이식.
    - SM-2 데이터를 FSRS 데이터로 변환하는 마이그레이션 로직 구현.

3.  **피드백 루프 개선 (Interactive Feedback)**:
    - 쓰기 연습 모달 종료 시, 유저가 자신의 체감 난이도를 4단계로 아주 가볍게 터치할 수 있는 'Zen Feedback' UI 추가.

---
**결론**: FSRS 도입은 단순한 코드 추가가 아닌 **시스템 아키텍처의 리빌딩**에 가깝습니다. 하지만 이 과정을 거치면 Mastery Board와 연동된 **"업계 최고 수준의 기억 관리 앱"**으로 진화할 수 있습니다.
